# DMDOD 視覚入力仕様

この文書は、DMDOD の Student を **構造化された 245D HUD 入力**から、**人間と同じ表示面を経由する pixel-based perception** へ移行するための観測仕様を定めます。

対象はまず **Level B: same display** です。

```text
Level A: same information
    人間が画面から得られるとみなした情報を構造化して直接入力
    現行 245D HUD policy

Level B: same display
    視覚情報は描画された pixels だけを通して入力
    ← この文書の対象

Level C: same perception
    視野・視線・視覚遅延・認識ノイズ・注視などまで人間相当にする
    将来課題
```

Level B の目的は、

> 「AI が人間に見える情報を使っている」

から一段進めて、

> 「AI も人間と同じように、画面上に描かれたものを視覚認識して判断する」

状態を作ることです。

---

## 1. 現行 Level A の整理

現在の v1.3 系 Student 入力は **245D** です。

### 1.1 233D base observation

`real_chart_features.py` の base observation は、

```text
MotorObservation                         6D
orbiting planet xy                      2D
15 floor slots × 15 features          225D
-------------------------------------------
                                      233D
```

です。

MotorObservation は、

```text
left_position
right_position
left_velocity
right_velocity
left_pressed
right_pressed
```

の 6 値です。

各 floor slot は、

```text
relative x/y
entry angle sin/cos
exit angle sin/cos
midspin
multi-planet flag
event markers
slot mask
```

を数値で直接持ちます。

これは「画面から取得可能な内容」に寄せていますが、**画像認識そのものは省略**しています。

### 1.2 HUD 12D

`real_chart_hud_features.py` でさらに、

```text
Tile BPM
Real BPM
feedback-visible
signed timing error
8-way judgement one-hot
```

の 12D を追加し、合計 245D になります。

Level B では、これらの視覚情報を scalar / one-hot channel として Student に直接渡してはいけません。

---

## 2. Level B の基本原則

Level B では Student の観測を、

```text
visual observation = rendered pixels
proprioception     = body state
```

に分離します。

人間も床の形や惑星位置は目で見ますが、自分の指の状態まで画面から推定しているわけではありません。

そのため、身体内部の感覚に対応する情報は pixel 化せず、別の proprioception channel として残します。

### 2.1 Student に直接渡してよいもの

Level B の policy に直接渡してよい非画像入力は、初期仕様では **MotorObservation 6D のみ**とします。

```text
left_position_m
right_position_m
left_velocity_m_s
right_velocity_m_s
left_pressed
right_pressed
```

これは身体感覚・キー接触感覚の近似です。

### 2.2 Student に直接渡してはいけないもの

以下は visual encoder を迂回して直接 policy に渡してはいけません。

```text
orbiting_x / orbiting_y
floor x / y
floor angles
floor relative index
midspin flag
num_planets flag
event marker flags
Tile BPM scalar
Real BPM scalar
judgement one-hot
signed timing error scalar
camera transform
visible floor count
frame timestamp
chart time
floor index
next target timestamp
time_to_next_target
XAcc / PP / score
progress
overload counter
Teacher timing
```

画面に表示されるものは、**pixels として描画された結果だけ**を Student が受け取ります。

---

## 3. Level B を B0 / B1 に分ける

いきなり「完全な実ゲーム画面」に移行すると、表現変更と表示仕様変更を同時に行うことになります。

そのため Level B は 2 段階に分けます。

### B0: representation bridge

現在の Level A が持つ exteroceptive information を、同じ範囲のまま pixel 化します。

```text
A:
structured geometry + structured HUD + proprioception

B0:
render(same geometry + same HUD) -> pixels
                              + proprioception
```

B0 の目的は、

> 「構造化 feature が強かったのか、pixel recognition でも同じ能力を得られるのか」

を比較することです。

B0 では現行と同じく、現在床を基準におおむね

```text
behind = 2 floors
ahead  = 12 floors
```

の scene data を renderer の入力に使って構いません。

ただし Student には floor slot 自体を渡しません。

### B1: same display target

B1 が本来の Level B です。

B1 では「何 floor 先まで」という構造的 cap ではなく、**カメラと viewport 上で実際に見えているもの**を描画します。

```text
full scene truth
      ↓
camera transform
      ↓
viewport clipping / overlap / occlusion
      ↓
rasterized frame
      ↓
Student
```

Student は、内部 scene object の存在や index を知りません。

---

## 4. Visual frame contract

初期実装の基準は次の通りです。

```text
resolution      320 × 180
channels        RGB
storage         uint8 or normalized float
render rate     60 Hz
policy rate     100 Hz
physics rate   1000 Hz
```

### 4.1 60 Hz visual / 100 Hz control

新しい visual frame がない control step では、直前の visual feature を保持します。

```text
time      0ms  10   20   30   40   50 ...
control    ●    ●    ●    ●    ●    ●
visual     ●         ●         ●       ...  approximately 60 Hz
```

実装上の描画周期は整数 step に丸めず、render clock を独立に管理します。

Student に、

```text
new_frame = true/false
frame_age_ms
render_timestamp
```

のような補助 scalar は与えません。

それらは視覚以外の timing side channel になるためです。

---

## 5. Frame に描くもの

B0/B1 共通で、少なくとも次を visual frame に含めます。

### 5.1 Play field

```text
stationary planet
orbiting planet
floor path
tile shape / direction
midspin visual
multi-planet visual
visible gameplay event icons / markers
```

惑星の正確な xy や床角度は Student には渡さず、rasterize された結果だけを見せます。

### 5.2 Camera

camera pan / zoom / rotation が存在する場合、それ自体も perception problem の一部です。

Student に camera matrix を直接与えてはいけません。

```text
scene
  ↓
camera
  ↓
pixels
```

のみとします。

B0 の最初の renderer では、比較を簡単にするため固定の canonical camera を使って構いません。

B1 では、実ゲームに合わせた camera semantics を実装します。

### 5.3 HUD

HUD は、**実際に表示面に存在するものだけ**を文字・アイコンとして描きます。

Level A で現在 scalar として渡している、

```text
Tile BPM
Real BPM
latest judgement
signed timing error
```

については、B0 では比較用 canonical HUD として画面に描いてよいものとします。

ただし B1 では、実際の対象 gameplay display に本当に表示される項目だけに限定します。

つまり B1 で Tile BPM や signed timing error が実画面に存在しないなら、それらは消します。

逆に、実画面で XAcc や combo などが常時見えているなら、B1 では「人間と同じ display」を優先して pixels に含めることを検討します。

この点は **実ゲーム screenshot と照合して固定する**まで未確定とします。

---

## 6. Pixel renderer の禁止事項

renderer は privileged chart truth を使って画面を描画して構いません。

実ゲーム renderer も内部 state から画面を描くためです。

ただし privileged truth が **画面以外の channel を通じて Student に漏れてはいけません**。

禁止例:

```text
RGB + exact angle vector
RGB + BPM scalar
RGB + next-target countdown
RGB + floor index embedding
RGB + hidden event flags
RGB + chart-time positional encoding
```

許可例:

```text
internal target time
      ↓
planet animation phase calculation
      ↓
RGB frame
```

Student が見るのが最終 pixels だけなら問題ありません。

---

## 7. Visual encoder

最初の reference architecture は、巨大な vision model ではなく小型 CNN にします。

例:

```text
RGB 320x180
    ↓
small CNN
    ↓
visual feature 128-256D
    │
    ├──── proprioception 6D
    ↓
fusion layer
    ↓
GRU hidden=128
    ↓
left/right motor action
```

重要なのは CNN の具体的な層数ではなく、**policy が structured geometry を直接見ないこと**です。

Visual encoder の出力次元は実装・benchmark で変更可能とします。

---

## 8. Recurrent state と frame reuse

policy は 100 Hz で動作し続けます。

60 Hz visual frame を CNN に通した visual feature は、新 frame が来るまで再利用します。

```text
new frame
   ↓
CNN
   ↓
visual feature cache
   ↓
100 Hz GRU control
```

これにより、同じ画像を毎 10 ms CNN に再投入する無駄を避けます。

proprioception は 100 Hz で毎 step 更新します。

---

## 9. Teacher は pixel 化しない

Teacher は引き続き privileged timing を使ってよいものとします。

Teacher は perception model ではなく、Student に正解 action label を与える教師です。

```text
privileged Teacher
      │
      └── teacher action labels

pixels + proprioception
      │
      v
Student visual policy
```

Teacher の privileged timing を画像に描画したり、Student feature に混ぜたりしてはいけません。

---

## 10. Dataset / guard / evaluation は原則共有

Level A と Level B を比較するため、可能な限り次を共有します。

```text
Train / Validation / Final split
body model
control dt
physics dt
Teacher
DAgger schedule
trust alphas
Validation guards
Anchor guards
Final charts
```

変えるのは基本的に、

```text
Observation representation
Policy front-end
```

だけです。

これにより、

```text
A: 245D structured HUD
B: RGB pixels + 6D proprioception
```

を比較できます。

---

## 11. 公平比較で固定する指標

A/B 比較時は少なくとも、

```text
completion / hit ratio
XAcc
Perfect rate
MAE
overload
TooEarly
Final holdout performance
```

を同じ evaluator で測定します。

さらに vision model では、

```text
training wall time
GPU memory
inference latency
visual encoder calls / second
```

も記録します。

---

## 12. Level B が成功したと言える条件

単に training loss が下がっただけでは不十分です。

最低でも、

1. structured floor geometry を一切 policy に直接渡していない
2. visual information は pixels のみから取得している
3. proprioception は MotorObservation 6D に限定されている
4. privileged timing leakage がない
5. 未知の Final charts でまともに進行できる
6. renderer の解像度・camera・HUD を固定して再現可能である

ことを要求します。

B0 では Level A との representation ablation が成立すれば成功です。

B1 ではさらに、実際の player display と renderer が十分一致していることを要求します。

---

## 13. Level C ではじめて扱うもの

Level B ではまだ、人間の知覚そのものまでは再現しません。

以下は Level C の対象です。

```text
visual processing latency
motion-to-photon latency
eye fixation / saccade
peripheral vision
acuity falloff
motion blur
recognition noise
attention limits
visual masking
human frame perception
```

つまり Level B の AI が人間より画像認識に強くても、それはまだ Level B の範囲内です。

---

## 14. 実装順序

推奨する実装順序は次の通りです。

```text
Step 1
B0 renderer
- current visible floor set
- planets
- canonical HUD
- 320x180 RGB

Step 2
Pixel observation type
- RGB frame
- MotorObservation 6D
- 60Hz visual / 100Hz control

Step 3
Small CNN + GRU policy
- visual feature cache
- same 2-finger action head

Step 4
Teacher trajectory / BC path 対応

Step 5
短い固定譜面で pixel policy smoke test

Step 6
Level A と同じ dataset で A/B comparison

Step 7
B1 renderer
- viewport-based visibility
- actual camera semantics
- actual gameplay HUD calibration
```

いきなり G 帯 training を pixel model で始めず、まず P 帯または短い known chart で perception path が成立していることを確認します。

---

## 15. 最終的な Student interface

Level B の policy-facing interface は概念的に次だけです。

```text
VisualMotorObservation
{
    rgb_frame: 320x180x3        # visual only
    proprioception: 6D          # MotorObservation
}
```

policy 内部は、

```text
rgb_frame
   ↓ CNN
visual feature ─┐
                ├─ fusion → GRU → motor action
proprioception ─┘
```

です。

**floor geometry・BPM・judgement・timing error を別 vector として併設しない**ことを Level B の最重要 invariant とします。
