# DMDOD 学習フロー

この文書は、現在の DMDOD の学習パイプラインを「何を学習していて、どこで候補を落として、何を採用しているのか」が追える形でまとめたものです。

基準は **v1.3.0 `aggregate-xacc`** です。

> 実装の細かい最適化よりも、まず学習アルゴリズムの流れを理解することを目的にしています。

---

## 1. 全体像

DMDOD は、ADOFAI の譜面を直接「正解入力時刻の列」として学生モデルに与えるのではなく、ゲーム中に人間が見える情報に近い HUD 観測から、身体モデルへの運動指令を出す方策を学習します。

```text
                        ┌─────────────────────┐
                        │   ADOFAI chart set  │
                        └──────────┬──────────┘
                                   │
                    chart-level split
                                   │
          ┌────────────────────────┼────────────────────────┐
          │                        │                        │
          v                        v                        v
      Train charts            Validation charts         Final charts
          │                        │                        │
          │                        │                        │
   teacher / DAgger          model selection only      最後の評価だけ
          │                        │                 （学習選択には使わない）
          │                        │
          └──────────────┬─────────┘
                         v
               ┌───────────────────┐
               │   Bootstrap BC    │
               └─────────┬─────────┘
                         v
               ┌───────────────────┐
               │   DAgger rounds   │
               │ sample → BC →     │
               │ trust region →    │
               │ guards → accept   │
               └─────────┬─────────┘
                         v
               ┌───────────────────┐
               │   trusted model   │
               └─────────┬─────────┘
                         v
               Validation / Final evaluation
```

大雑把には、

1. Teacher の動きを模倣して初期方策を作る
2. Student 自身を実際に動かす
3. Student が遭遇した状態で Teacher に正解行動を付けてもらう
4. そのデータで BC（Behavior Cloning）する
5. いきなり全更新を採用せず、小さい trust-region step を複数試す
6. Train / Validation / Anchor を壊していない候補だけ採用する
7. これを繰り返す

という流れです。

---

## 2. Student が見ているもの

現在の方策入力は **245D HUD observation** です。

主な構成は、

- 画面から分かるタイル幾何
- 指・キーの身体状態
- Tile BPM
- Real BPM
- 一時的な判定結果
- 一時的な signed timing error

です。

一方、Student には本番で次のような「答えそのもの」は見せません。

- 次の正解入力時刻
- `time_to_next_target`
- 譜面の絶対時刻
- floor index の内部真値
- XAcc
- 進捗率
- overload counter の内部値
- Teacher が使う privileged timing

現在の標準構成では、

```text
HUD input          245D
hidden size        128
policy step        10 ms (100 Hz)
physics step        1 ms (1000 Hz)
body               2 fingers, same-hand
```

です。

Teacher は学習用ラベルを作るときだけ、Student より強い timing 情報を使えます。現在の較正では single-press lead はおよそ **43 ms** です。

つまり、

```text
Teacher: 正解 timing を知っている教師
Student: HUD だけを見て予測して動く実働 AI
```

という役割分担です。

---

## 3. Dataset の役割

DMDOD は譜面単位で `Train / Validation / Final` を分離します。

### Train

実際に学習する譜面です。

Train chart からは主に、

- bootstrap 用の固定 anchor
- start-micro segment
- round ごとにランダムに切り出す `round-train` segment

を作ります。

### Validation

gradient 学習には使いません。

更新候補が、未知の Validation 譜面で以前より大きく壊れていないかを確認するために使います。

### Final

学習中の候補選択には使いません。

最終 checkpoint を評価するときだけ使用します。

そのため、一度 Final 結果を見たあと、その結果を参考に設計や学習を変更した場合、その Final split は以後「完全に pristine な holdout」とは扱えません。

---

## 4. Anchor とは

Anchor は、Train 譜面上の固定された評価区間です。

目的は、ある round で新しい区間を学習した結果、以前できていた Train の別区間を忘れる **catastrophic forgetting** を防ぐことです。

通常 anchor に加えて、v1.0 以降は **start-micro** があります。

start-micro は譜面開始直後だけを切り出した短い区間で、GRU の初期状態から意味不明な早押しをする startup transient を抑えるために追加されました。

```text
Train chart
│
├─ normal anchor 1
├─ normal anchor 2
└─ start-micro
```

短い譜面では normal anchor の位置が重複するため、実際の anchor 数は単純な `Train charts × 3` にはなりません。

---

## 5. Bootstrap

最初から Student を自力でプレイさせても何もできないため、まず Teacher の trajectory を使って Behavior Cloning します。

```text
Teacher trajectory
      │
      v
observations + teacher actions
      │
      v
recurrent BC
      │
      v
bootstrap candidate
```

warm-start を指定した場合は、以前の checkpoint から **model weights だけ**を読み込み、そのモデルを epoch 0 の候補として新しい dataset 上で再評価します。

現在の v1.1 以降では、bootstrap candidate の優先順位は概ね、

```text
1. overload safety
2. start-micro が clean か
3. start-micro TooEarly が少ないか
4. completion
5. XAcc
6. Perfect rate
7. TooEarly の少なさ
```

です。

つまり、少し精度が高い代わりに開始直後に誤爆するモデルより、まず安全で start が clean なモデルを残します。

bootstrap で選ばれたモデルが、その後の round 学習の **trusted model** になります。

---

## 6. 1 round で何をしているか

1 round の本体は DAgger です。

```text
trusted model
    │
    ├─ Train chart を1つ選ぶ
    │
    ├─ 30秒前後の train window を切り出す
    │
    ├─ Student / Teacher mixture rollout
    │
    ├─ 遭遇した observation に Teacher action を付ける
    │
    └─ BC proposal を作る
              │
              v
       trust-region line search
              │
              v
       guards を通ったら ACCEPT
```

### 6.1 DAgger rollout

Student を実際に現在の方策で動かし、Student が到達した状態を集めます。

その状態に対して Teacher action をラベルとして保存します。

普通の単純な BC と違い、

> 「Teacher だけが通る綺麗な状態」ではなく「Student が実際にミスしながら到達する状態」

を学習できるのが DAgger の重要な部分です。

---

## 7. BC proposal

現在の trusted model を起点に、fresh Adam で BC proposal を作ります。

sequence 順序による偏りを減らすため、round epoch では概ね、

```text
odd epoch   : forward order
even epoch  : reverse order
```

を交互に使います。

重要なのは、BC proposal をそのまま採用しないことです。

BC は Teacher loss を改善しても、実際のゲーム挙動では別の区間を壊すことがあります。

そのため次の trust-region line search に進みます。

---

## 8. Trust-region line search

proposal と trusted model の間を補間し、複数の更新量を同時に試します。

現在の alpha は、

```text
1.0
0.5
0.25
0.125
0.0625
0.03125
```

です。

概念的には、

```text
candidate = trusted + alpha * (proposal - trusted)
```

です。

`alpha=1` は BC proposal 全部、`alpha=0.03125` は非常に小さい更新です。

各 alpha candidate を実際の simulator でプレイさせ、次の guard を順番に通します。

---

## 9. v1.3 の guard

現在の順番は、

```text
Train guard
   ↓
Validation local guards
   ↓
Validation aggregate XAcc
   ↓
Anchor local guards
   ↓
Anchor aggregate XAcc
   ↓
complete candidate
```

です。

### 9.1 Train guard

v1.1 までは、sampled train window で **base より改善すること**が必須でした。

P7-P10 の大きい dataset ではこれが強すぎて、ほとんどの候補が Validation に到達する前に `not-better` で死亡しました。

v1.2 から sampled train window は「最適化対象」ではなく **non-regression safety gate** です。

現在は主に、

- safe → overload を禁止
- hit の大幅低下を禁止
- XAcc の大幅低下を禁止
- TooEarly の大幅増加を禁止

します。

「この30秒で必ず改善しろ」とは要求しません。

---

### 9.2 Validation local guard

v1.3 では、各 Validation segment ごとに hard guard として、

- overload
- hit regression
- TooEarly regression

だけを見ます。

XAcc はここでは判定しません。

以前は各 segment ごとに `XAcc -2pt` を hard reject していましたが、Validation が16本、Anchor が約190本ある状態では、全体として良い更新でもどこか1区間だけ 2pt を超えて落ちて全候補死亡しやすくなっていました。

---

### 9.3 Validation aggregate XAcc

全 Validation segment の local hard guard を通った candidate について、XAcc を role 全体でまとめて判定します。

現在は target 数で重み付けした XAcc を使い、

```text
candidate Validation XAcc
    >=
reference Validation XAcc - 2pt
```

を要求します。

つまり、ある1譜面で少し精度を落としても、Validation 全体として floor を守れていれば先へ進めます。

---

### 9.4 Anchor guard

Anchor も同様です。

各 anchor では、

- overload
- hit regression
- TooEarly regression

を hard guard にし、XAcc は全 anchor を target-weighted aggregate して最後に判定します。

start-micro も anchor role の一部です。

---

## 10. Candidate の最終採用

Validation と Anchor を全部通っただけでは、まだ採用しません。

v1.2 以降は trusted base 自身も同じ guard surface で評価し、complete candidate が **全体として trusted model より良いか**を比較します。

現在の aggregate ranking は概ね、

```text
1. safety
2. start-clean
3. start-micro TooEarly
4. completion / hit ratio
5. weighted XAcc
6. weighted Perfect rate
7. TooEarly
8. misses
```

です。

candidate が trusted model を超えなければ rollback します。

複数 candidate の gameplay 指標が完全に同じなら、より小さい alpha を選びます。

```text
complete candidate exists
      │
      ├─ aggregate > trusted  → ACCEPT
      │                         trusted model を更新
      │
      └─ aggregate <= trusted → ROLLBACK
```

---

## 11. Reference floor は ratchet する

Validation / Anchor の reference は、一度良くなったら簡単には下げません。

accepted candidate が reference より良ければ、その segment の reference を更新します。

```text
old floor
   ↓
better accepted model
   ↓
new higher floor
```

このため学習が進むほど anti-forgetting constraint は強くなります。

これは過去能力を守るための仕組みですが、厳しすぎると固定点になるため、v1.2 / v1.3 では guard の粒度を調整しています。

---

## 12. Fixed-point skip

同じ trusted state から作った deterministic な forward / reverse proposal が両方 reject された場合、そのまま同じ状態で残り epoch を計算しても同じ結果になることがあります。

その場合は round の残り epoch を skip します。

ログの、

```text
fixed-point skip=14
```

は、16 epoch のうち forward / reverse の2候補を試した時点で固定点と判断し、残り14 epoch を省略したという意味です。

---

## 13. 学習結果と評価指標

ログでよく見る指標は以下です。

| 表記 | 意味 |
|---|---|
| `H` | hits / total targets |
| `miss` | miss 数 |
| `X` | X-Accuracy |
| `PP` | Perfect 系判定率 |
| `MAE` | hit timing error の平均絶対値 |
| `early` | TooEarly press 数 |
| `overload` | overload failure が発生したか |
| `keydowns` | 物理 KEY_DOWN 回数 |

### overload 時の注意

overload すると simulation が途中で終わる場合があります。

そのため、

```text
H + miss < total targets
```

になることがあります。

この場合、残りは「miss として最後まで数えた」のではなく、simulation がそこまで到達していない target です。

したがって overload した結果の XAcc / PP / MAE は、生存した区間だけで計算されて見かけ上よくなることがあります。

G 帯などで「クリアできるか」を見るときは、まず overload と completion を優先して確認する必要があります。

---

## 14. STRICT 評価

trainer 内部の candidate selection と、ADOFAI `Strict` 相当の外部評価は別物です。

現在は、Strict の汎化性能を確認するときは、例えば

```text
scripts/eval_v110_strict_dataset.py
```

のような評価専用スクリプトを使います。

Strict 結果は「学習後にどれだけ通用するか」を見るもので、通常の round candidate 選択そのものには直接入っていません。

## 15. 高速化はどこに入っているか

現在は simulator evaluation が重いため、多数の execution-only optimization が入っています。

これらは基本的に「何を ACCEPT するか」ではなく「同じ判定をどれだけ速く計算するか」を変えます。

### CUDA BC

BC proposal は RTX GPU 上の packed GRU で計算できます。

```text
CPU simulator / guards
GPU BC proposal
```

という分担です。

### adaptive guard waves

生き残っている alpha candidate 数に応じて、Validation / Anchor を何本ずつ worker に投げるかを変えます。

多数 candidate が生きているときに大量の anchor を先読みして無駄計算するのを防ぎます。

### forward guard / reverse BC overlap

forward proposal の guard を CPU が評価している間に、同じ trusted state から reverse proposal を GPU で先行計算します。

```text
GPU:  forward BC ───── reverse BC prefetch ─────
CPU:             forward guard ───── reverse guard
```

forward が reject されれば prefetched reverse proposal をそのまま使えます。

forward が ACCEPT されて trusted state が変わった場合は、古い reverse prefetch を捨てて正しい base から再計算します。

### caches

- Teacher trajectory disk cache
- exact BC proposal cache
- simulator evaluation cache
- CUDA sequence cache

などがあります。

cache hit は計算を省略しますが、同じ exact key の結果しか再利用しません。

## 18. 疑似コードで全部まとめると

```python
# chart-level split
data = load_dataset()
train, validation, final = data.Train, data.Validation, data.Final

# fixed Train anchors + start-micro
anchors = build_anchors(train)

# privileged teacher labels
expert = collect_teacher_trajectories(anchors)

# initial policy
trusted = warm_start_or_random_model()
trusted = bootstrap_behavior_cloning(trusted, expert)

for round in rounds:
    # Student が実際に遭遇する状態を集める
    segment = sample_train_window(train)
    dagger_rollout = collect_student_teacher_mixture(trusted, segment)
    sequences = build_round_training_set(expert, dagger_rollout)

    for parity in [forward, reverse, ...]:
        proposal = behavior_clone_from(trusted, sequences, parity)

        complete = []
        for alpha in [1, .5, .25, .125, .0625, .03125]:
            candidate = interpolate(trusted, proposal, alpha)

            if not train_non_regression(candidate):
                continue

            if not validation_local_safety_hit_early(candidate):
                continue
            if not validation_aggregate_xacc(candidate):
                continue

            if not anchor_local_safety_hit_early(candidate):
                continue
            if not anchor_aggregate_xacc(candidate):
                continue

            complete.append(candidate)

        improving = [
            c for c in complete
            if aggregate_guard_surface_key(c) > aggregate_guard_surface_key(trusted)
        ]

        if improving:
            trusted = best(improving)
            ratchet_validation_and_anchor_references(trusted)
        else:
            rollback_to(trusted)

        if forward_and_reverse_reject_same_trusted_state():
            break  # fixed-point skip

# selection に使わなかった Final を最後に評価
report(validation, final)
```

## 19. G 帯へ進むときの考え方（未実装部分）

ここから先は現行 v1.3 の実装ではなく、G 帯 curriculum の方針候補です。

P 帯では既に一部譜面で FC に近い挙動が出ているため、G では最初から XAcc を最大化するより、

```text
1. overload しない
2. 最後まで生存する
3. hit / completion を上げる
4. 最後に XAcc / PP を詰める
```

という順序が自然です。

候補としては、

```text
P7-P10 checkpoint
      │
      v
G1-G4 warm-start curriculum
      │
      ├─ P replay を一部残す
      ├─ failure-centered segment mining
      ├─ survival / completion first selection
      │
      v
G5-G7
      │
      v
G8-G10
```

を想定しています。

特に、G 譜面で毎回同じ場所で崩れるなら、完全ランダムな30秒だけではなく、失敗地点前後を優先して DAgger する **failure-centered mining** が重要になる可能性があります。

---

## 20. 一言でまとめると

DMDOD の現在の学習は、

> **Teacher を模倣して proposal を作り、Student を実際にゲームで動かし、過去能力を壊さない範囲だけ trust-region で少しずつ採用する recurrent DAgger**

です。

そして v1.2 / v1.3 の変更は、

> **「何か1区間でほんの少し悪くなっただけで全更新を殺す」状態から、全体性能を保ちながら新しい技能を獲得できるようにする**

ための調整です。
